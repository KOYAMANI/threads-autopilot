# 公開済み投稿の上限と再開

`0009_queue_publish_safety.sql` で `queue.root_published_at` を追加する。Threads APIからroot公開成功の応答を得た時刻を、最初の `result_ids_json` と同じUPDATEで保存する。以後の返信失敗・再試行・編集・取消でこの日時を変更しない。DB triggerも日時の上書きやNULLへの戻しを拒否する。

公開直前の上限は、この日時をアカウントのタイムゾーンで集計する。`done` / `publishing` / `failed` / `cancelled` などの状態や `updated_at` に左右されない。APは最大3件/日、手動投稿はAP専用の3件制限の対象外（アカウント共通の投稿上限・投稿間隔は適用）。返信に失敗したrootも投稿間隔に含む。

画像コンテナは作成日と公開日が異なりうるため、step 1のroot公開直前にも上限・間隔・重複を再検証する。step 0/1へ戻された行にすでにroot IDがあれば、新しいrootを作らず残りの返信から再開する。rootの `posts.posted_at` も返信完了日へずらさない。

AP OFFと実行が競合した場合は、`scheduled` から `publishing` へ変える単一SQLで現在の `ap.enabled` を確認する。読取後にOFFになっても新たな送信権を取得できない。先に `publishing` を取得した処理は開始済みとして扱い、OFFで外部への送信をロールバックできるとは表示しない。OFFの予約が残っていても手動予約の実行を妨げない。

旧データは公開IDが残る行だけを移行する。保存済みroot投稿の日時をUTC ISO形式へそろえて優先し、取得できない場合は旧 `updated_at` を保守的な代替値にする。過去の正確なAPI応答時刻を復元できるわけではない。新形式では公開成功時に記録する。

公開済み行の削除拒否はqueue API側の対応と合わせて利用する。ユーザー/アカウント削除は通常のデータ削除方針に従う。

今回の変更は、API成功応答を受け取った後の保存・返信失敗・再開・状態変更に対する対策。外部APIが成功した直後に応答を失ったり、WorkerがD1保存前に停止したりする不確定状態までexactly-onceを保証するものではない。実サービス間にまたがるこの境界は別の再照合・不明状態管理を要する。

検証: publish / publish-safety / posting-slotsの39テスト、型チェック、差分チェックを通過。独立したインメモリSQLiteで0009の旧日時移行・未公開行維持・日時の変更拒否も確認。実アカウントへの投稿は行っていない。
