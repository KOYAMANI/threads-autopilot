# 生徒への共通URL配布：セキュリティ・容量・復旧レビュー

2026-09-07 / 対象 threads-autopilot / commit 4a83d0f / 配布形態：共通URLで各自ログイン / 人数：未確定

**判定：現状のまま一般配布することは勧めません。** ユーザー単位のアクセス制御と秘密情報の暗号化はあります。ただし、ログアウト時のキー残留、自動処理の登録漏れ、パスワード再設定の競合が再現しました。配布前に修正と再検証が必要です。

## 1. 質問への回答

| 質問 | 現時点の回答 |
| --- | --- |
| 生徒のAPIキーは安全？ | サーバー保存分はAES-256-GCMで暗号化され、設定APIはキーの有無だけを返します。ただし端末保存分はログアウトしても残ります。「安全です」とはまだ言えません。 |
| 他の生徒の情報は見えない？ | サーバーはログインユーザーの所有権を確認します。2ユーザーの隔離テストでも他人のキューは404、参考情報・AIキーは混ざりませんでした。一方、同じブラウザを使い回す場合のキャッシュとキーの残留は確認しました。 |
| 大人数でもDBは耐える？ | 人数だけでは判断できません。現状はDB容量より先に、自動処理を登録するコードの上限に当たります。修正後に同時アクセスと予約投稿を含む負荷試験が必要です。 |
| データが消えない保証はある？ | 絶対保証はありません。DB保存はされていますが、誤削除・鍵紛失・復旧失敗への備えは別途必要です。バックアップから実際に戻せることをまだ確認できていません。 |

## 2. いまの構造を平たく言うと

生徒のブラウザ → 共通のCloudflare Worker（受付・本人確認・処理）→ 共通のD1（データの保管庫）という構造です。WorkerはGemini/OpenRouter、Threads、メール・Pushサービスにも接続します。定期処理も同じD1のjobsテーブルを使います。

D1はSQLiteをベースにしたDBです。生徒ごとに別DBがある構成ではなく、1つのDBの行にuser_id / account_idを付けて分けています。隔離はWorkerの所有権チェックに依存します。UIで別アカウントを選べなくするだけでは不十分で、サーバー側のチェックを全経路で維持する必要があります。

「アプリにログインする生徒」と「その生徒が接続するThreadsアカウント」は別です。AIキーと参考情報は生徒単位、投稿・予約キューはThreadsアカウント単位です。以下の16件・32件という数字は、生徒数ではなく接続Threadsアカウント数です。

ローカル開発は .wrangler/state 以下のファイルにDBを保存します。wrangler.tomlのdatabase_idはゼロ埋めの仮値、APP_ORIGINもlocalhostです。実際の公開先のD1、契約プラン、Secrets、TLS、アクセス権、バックアップ状況は、このコードだけでは確認できません。**localhostのDBにクラウドの復旧機能が付いているとは扱えません。** package.jsonのcleanスクリプトは .wrangler も削除するため、実行するとローカルDBを失います。

## 3. 配布前に直すべき発見事項

### P1-1：ログアウトしても前の生徒のAPIキーとキャッシュが残る【再現済み】

web/src/api/auth.ts:41-46 は、ログアウト成功時にmeだけをnullにします。web/src/api/ai.ts:31-58 は、ユーザー名の付いていないlocalStorage.aiKeyを共通で読み書きします。AI設定・参考情報のキャッシュキーもユーザーIDを含みません（同ファイル:63,96）。

生徒Aが「端末に保存」を選んでキーを入力 → ログアウト → 同じブラウザで生徒Bが端末保存モードを使うと、Bの生成リクエストにAのキーが付く経路があります。キーを知らないBがAの課金枠を使うことにもつながります。ダミーlocalStorageと実際のフックの成功コールバックを使い、キーと参考情報キャッシュが残ること、withClientKeyが次ユーザーのリクエストにも旧キーを付けることを確認しました。ブラウザでの2ユーザー全操作を通したE2Eではありません。

別々の端末を使う無関係な生徒同士のキー漏洩を確認したわけではありません。ただし学校PC・家族共有PC・複数ログインのある端末では配布時に起こり得ます。

修正：ログアウト・認証失効・ログイン主体変更で通信を中止し、QueryClientと画面状態を破棄。キャッシュをuserId単位に分離し、遅れて返る旧通信も採用しない。キーの端末保存は廃止またはメモリ限定を優先し、維持するならユーザー別名前空間とログアウト削除を必須にします。localStorageをユーザー別にするだけではXSSへの防御にはなりません。

同一生徒内のThreadsアカウント切替でも、以前のレビューで投稿本文の残留を確認済みです。画面の再マウントまたはaccountId別の下書き保存を行い、送信開始時の所有者IDを固定して、別アカウントへの誤投稿を防ぎます。

### P1-2：アカウント増加で定期処理を登録しきれず、後方のアカウントが取り残される【再現済み】

worker/src/lib/jobs.ts:103 の台帳予算は190クエリ。新規ジョブ登録は重複確認＋INSERTの2クエリです（:171-198）。毎回古いアカウントから走査し（:234-235）、毎時は3ジョブ、平日日次は6ジョブを各アカウントに登録します。予算超過を握りつぶし（:215-222）、継続位置を保存しません。

| 隔離テスト条件 | 結果 |
| --- | --- |
| 未処理ジョブなし・32アカウント・毎時 | 予定97件に対し94件で登録終了。その呼び出しのrunJobs冒頭も予算超過で失敗。 |
| 未処理ジョブなし・16アカウント・月曜日の日次 | 予定97件に対し94件で登録終了。その呼び出しのrunJobsも失敗。 |
| 100アカウント・毎時を2回。間に登録済みジョブをすべて完了扱いにする | 2回とも先頭側から再登録。到達したのは32アカウントで、100番目には一度も登録されない。 |

これはD1の性能測定ではなく、アプリの制御ロジックの再現テストです。すべての機能が16件・32件で止まるという意味でもありません。既存pendingジョブや曜日により条件は変わり、5分ごとの別呼び出しで登録済みの仕事は進められます。ただし未登録の仕事は処理できず、後方のアカウントに不公平が残ります。

修正：投入対象をページ分割し、継続カーソルと周期IDを永続化。周期ID＋種類＋アカウントの一意性をDBで保証し、投入と処理の予算を分離します。障害後の再開・公平性・全件到達を検証してください。規模に応じてCloudflare Queues等で分配する構成も検討対象です。定数190を増やすだけでは解消しません。

### P1-3：拒否したパスワード再設定がパスワードを書き換える【再現済み】

worker/src/routes/auth.ts:469-476 は、パスワードを書き換えてからトークン消費の成功を確認します。同じ有効トークンのリクエストA/Bが「未使用」の読み取りを終えたところで競合させると、Aは200、Bは400なのに、Aの新パスワードでログインすると401、Bの新パスワードだと200になりました。

悪用には有効な再設定トークンと競合条件が必要です。トークンなしで誰のパスワードでも変えられるという問題ではありません。

修正：トークンの検証・一度だけの消費・パスワード更新・セッション無効化を、失敗時に部分更新を残さないDB操作として設計します。単に消費を先に移すだけでは、その後の障害で未変更のままリンクだけ無効になるため、競合と途中失敗の両方を試験します。

### P1-4：復旧手順が共通DB・外部投稿・暗号鍵を含めて検証されていない【運用上の不足】

READMEに手動Time Travel復旧の説明はありますが、独立した定期バックアップ、鍵の復旧、定期的な復元試験の実装・実施記録は確認できません。投稿CSVは最大5,000件の投稿・指標の書き出しであり、予約・参考情報・設定・鍵を含む完全バックアップではありません（worker/src/routes/export.ts:153以降）。

D1 Time TravelはDB全体をその場で巻き戻します。共通DBでは生徒Aの誤削除だけを直したつもりでも、他の生徒の新しい更新も巻き戻ります。Threadsに投稿済みの内容はDB復旧で取り消せません。復旧したキューが投稿前の状態に戻ると、再投稿するリスクもあります。復旧前の自動処理停止と、外部投稿IDとの照合を手順に含めてください。

### P2-1：共有サービスとしての件数・通信量制限が不足【コード確認】

参考情報の登録にユーザー別総件数・総容量の上限がなく、本文を全件読み出してからプレビューを作っています（worker/src/routes/sources.ts:80-89）。1件の保存本文上限はありますが、件数を増やせます。Push購読も任意件数を追加できる経路です。1人の大量操作で共通DB・Worker・外部APIの負荷が増えます。

ログインはメール別、AI呼び出しはユーザー別などの制限がありますが、登録や参考情報追加を含む全体の防御ではありません（worker/src/lib/rate.ts）。ユーザー別の保存容量、登録数、生成回数・費用上限、リクエスト本文上限、IP単位の入口制限を設定してください。参考情報一覧はページ分割し、必要な列だけをDBから返します。

### P2-2：共有端末のPush通知がログアウト後も紐付いたまま【コード確認・配送未試験】

ログアウトはセッションだけを削除します。Push購読のIDはuserId＋endpointから作るため、同じブラウザの購読先が別々のユーザーに登録できます（worker/src/routes/notifications.ts:123-131,163-168）。旧ユーザーへの通知が共用端末に届く可能性があります。

ログアウト時にその端末のサーバー側購読を解除し、ブラウザ側も購読解除。ユーザー切替時に端末の通知所属を付け替えます。失敗時の再試行も含め、実際の端末で確認してください。

### P2-3：認証・ブラウザ防御・鍵運用を強化する余地【コード確認】

パスワードはPBKDF2-SHA256の100,000回です（worker/src/lib/crypto.ts:8）。OWASPの同方式の推奨は600,000回です。Workersの実行制約とログイン遅延を検証したうえで、適切な方式への移行または認証基盤の利用を検討します。既存ユーザーをログイン時に移行できるよう、方式・コストのバージョンを記録してください。[OWASP公式](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

CSP等のセキュリティヘッダー設定はリポジトリでは見つかりませんでした。認証APIのno-store、CSP、frame-ancestors、nosniff、Referrer-Policyを設計し、静的HTMLを含む実際の公開レスポンスで検証してください。未設定だけでXSSが成立するという指摘ではありません。

サーバー保存の秘密は共通ENC_KEYで復号します。DBだけの漏洩への防御はありますが、Workerの実行権限と鍵を得た運用者・侵入者には復号可能です。生徒本人しか読めない暗号方式ではありません。管理者権限の最小化、MFA、Secretsへのアクセス制限、別管理の鍵バックアップ、鍵バージョンとローテーション手順が必要です。

「端末にだけ保存」も、AI実行時にはclientKeyとしてWorkerへ送信します。サーバーに永続保存しないという意味で、サーバーを通らないという意味ではありません。参考情報や生成指示もAI事業者へ渡るので、生徒向け説明には送信先と対象データを明記してください。

### P2-4：依存パッケージに公開アドバイザリ【依存監査済み・悪用未再現】

npm audit --omit=dev はmoderateの対象パッケージ2件（react-routerと、それに依存するreact-router-dom）、high/criticalは0件でした。react-routerに2つのアドバイザリがあります。「2パッケージ」は独立した2つの侵入経路を意味しません。

SSR hydrationの問題は、現在のBrowserRouterによるSPA構成では該当しないと評価します。外部リダイレクトの問題も、確認した画面遷移は固定パス中心で、攻撃者入力からの成立経路は確認していません。修正版への更新計画を立て、メジャー更新の画面回帰を確認してください。audit fix --forceは実行していません。[React Router：リダイレクト](https://github.com/remix-run/react-router/security/advisories/GHSA-wrjc-x8rr-h8h6) / [SSR hydration](https://github.com/remix-run/react-router/security/advisories/GHSA-337j-9hxr-rhxg)

## 4. すでにできている防御

- APIキー・ThreadsトークンはAES-256-GCM、ランダムIVで暗号化。ダミーキーの暗号文保存と復号をテストしました。
- 設定取得APIは保存キー本体を返さず、hasKeyを返します。別ユーザーにはそのキーがある扱いにもなりません。
- セッションCookieはHttpOnly・Secure・SameSite=Strict。変更系APIはX-Requested-Withを検証します。
- 調査したデータAPIはログインユーザーの所有権を確認し、SQLはバインドパラメーターを使っています。代表的な越権アクセスも隔離テストで拒否されました。
- ライセンス失効時はログインと自動投稿・計画処理に停止チェックがあります。
- 本番でメール送信キー未設定の場合、パスワード再設定リンク本文をログ出力しない分岐があります。

これらは良い土台ですが、全API・全競合条件の安全性を証明するものではありません。

## 5. 何人まで使えるかを決める方法

Cloudflare公式の現行制限ではD1は1DBあたりPaid 10GB / Free 500MB、1回のWorker実行のD1クエリはPaid 1,000 / Free 50です。現在の800＋190という予算設計はPaid前提です。1つのDBはクエリを順番に処理するので、速度はクエリ時間や同時負荷に左右されます。上限人数の保証にはなりません。[D1公式制限](https://developers.cloudflare.com/d1/platform/limits/)

このアプリでは「人数 × 1人の接続アカウント数 × 投稿・同期頻度」が主な負荷になります。授業開始時の一斉ログイン、一斉AI生成、同時刻の予約投稿も測定対象です。

修正後、隔離した本番相当環境で50 / 100 / 300ユーザーなど段階的に試験し、各段階でアカウント数・同時利用数を明示します。この数字は試験例であり、対応可能人数ではありません。DBサイズは本文・指標履歴・索引を含む実測の「1人1日あたり増加量」から保存期間込みで見積もります。

合格条件例：他人のデータ混入0、ジョブ未登録0、重複投稿0、取り残されるアカウント0、DB overloadedの継続発生0。画面APIのp95応答時間、予約時刻から投稿までの遅延、未処理ジョブの最古待ち時間、DB容量・読書き量、外部API費用を監視します。時間の基準は提供するサービスの約束に合わせて決めます。

まず投入処理の不具合とページ分割を直し、単一D1で測定します。必要性を測る前に別DB製品へ全面移行する必要はありません。容量や競合が限界に近づいたら、生徒群ごとのDB分割などを検討します。

## 6. 「消えない」より「どこまで・何時間で戻せる」を決める

D1 Time Travelは自動で履歴を持ち、Paidは過去30日、Freeは7日まで復旧できます。復旧は既存DBへの上書きで、現在はTime Travelから別DBへの直接クローンには対応していません。これはクラウドD1の機能で、今回のローカルDBに対して復元実験をしたわけではありません。[D1 Time Travel公式](https://developers.cloudflare.com/d1/reference/time-travel/)

運用では、Time Travelに加え、完全な定期エクスポートを本体と権限を分けた非公開保存先へ世代管理します。秘密や個人情報を含むバックアップにもアクセス制限・暗号化・保存期限を設定します。ENC_KEYはDBバックアップと別に安全に保管し、鍵バージョンと対応するデータを復元可能にします。

復旧手順は、①自動投稿と書込み停止、②障害直前の状態を退避、③対象時点・全生徒への影響を判断、④DBと鍵を復元、⑤投稿済みID・予約・取り消し・退会・失効済みセッションを照合、⑥隔離を確認して段階再開、です。誤削除された一人分だけの復旧方法も別途用意します。

例として「独立バックアップで最大24時間分の変更まで失う可能性を許容（RPO）」「4時間以内の復旧を目標（RTO）」を置き、復元演習で実測します。これは現時点の達成値でも保証でもありません。生徒への約束は、試験で達成できた値を根拠に設定してください。画面上の未保存原稿やlocalStorageのキーは、D1のバックアップでは戻りません。

## 7. 配布へ進める順序

1. キー・キャッシュ・Pushのユーザー切替処理、パスワード再設定、ジョブの全件登録を修正し、回帰テストを追加する。
2. 本番用のD1・HTTPS・APP_ORIGIN・Secrets・管理者権限を整備し、開発用DB・デモアカウントを分離する。
3. バックアップと暗号鍵からの復元を演習し、外部投稿との整合性も確認する。
4. 人数・同時利用・アカウント数を決めて負荷試験する。利用上限と監視を入れる。
5. 少人数の試験提供で監視し、合格条件を満たした範囲まで段階的に拡大する。

## 8. 検証範囲と証拠

今回のセキュリティ再現試験はテスト専用のCloudflare環境とダミーユーザー・ダミーキーを使用し、実アカウントへの投稿やメール配送をしていません。通常アプリのソース修正・本番デプロイは行っていません。

既存テストはshared 85件・worker 380件の計465件が成功。監査追加の6ケースも成功しました（不具合を再現できることを期待するテストを含むため、「成功＝安全」ではありません）。初回の監査試験では準備データのID重複により2件失敗し、テスト準備を修正後、workerの5ケースすべてが成功しました。追加フロント側1ケースも成功済みです。初期レビューでtypecheckは成功しています。

証拠ファイル：audit-evidence/security-capacity-review.test.ts、audit-evidence/security-browser-review.test.ts、audit-evidence/npm-audit.json。テストは既存worker/testとshared/testに一時配置して実行しました。証拠として保存した後、一時配置は除去しています。再現コードは現状の不具合を期待値にした監査用であり、修正後の回帰テストでは期待値を反転させる必要があります。

未確認：公開環境の実設定、実際の生徒数とデータ量、クラウド上の負荷試験、バックアップ復元演習、Push実配送、全APIの網羅的侵入試験。したがって、安全性認証や無損失保証を出すレビューではありません。
