## 優先して直す不具合

### 1. [P1・画面で再現] アカウント切替で前の原稿が残り、保存・投稿先だけ切り替わる

**再現:** `@demo_yama` で3案生成 → ヘッダーから `@demo__b` へ切替。生成済み本文と候補がそのまま残り、「キューに入れる」で日時確認まで進める。確認シートには投稿先アカウント名がない。投稿は確定していない。

**原因:** `Create` のローカル状態はaccount IDに結びついていない。一方、`useCreateQueue(account?.id)` は選択先のIDへ切り替わる。`Shell` の画面キーもpathnameのみ。

参照: `web/src/screens/Create.tsx:50`、同`:57`、同`:203`、`web/src/api/queue.ts:86`、`web/src/components/Shell.tsx`。

**修正:** 原稿・候補・素材選択・修正履歴をアカウントごとに保持。非同期生成の戻り先も開始時のアカウントに固定する。最終確認には投稿先、本文プレビュー、日時を明示する。

**受け入れ条件:** A→B→Aで各原稿が独立して復元される。Aの生成中にBへ切り替えても結果がBへ流入しない。

### 2. [P1・画面で再現] 案を見比べるだけで手動編集が消える

**再現:** 生成した案Aの本文を「レビュー用：案Aに手動で加えた編集」に変更 → 案B → 案A。元の生成本文に戻り、手動編集が消える。

**原因:** `pickCandidate()` が毎回 `setDraft(draftOf(c))` で元候補を読み直す。手動編集を候補側に保存していない。

参照: `web/src/screens/Create.tsx:95`。

**修正:** 候補IDごとの編集状態を保持し、切替前に編集を保存する。既に選択中の案をクリックしても編集を初期化しない。

**受け入れ条件:** 本文とコメントをそれぞれ編集してA→B→C→Aと戻っても全編集が残る。

### 3. [P1・画面で再現] 日本語167文字を501文字と表示し、入力上限を超える

**再現:** 手書き本文に「あ」を167個入力。カウンターは `501 / 500`、エラーは「本文は500文字までです（いまは501文字）」になる。

**原因:** `bodyLength()` がコードポイント数とUTF-8バイト数の大きい方を返す。一般的な日本語1文字が3として数えられる。コードコメントでは実API実測待ちの暫定対応と明記されているが、UIは「文字」と案内している。

参照: `shared/src/validate.ts:31`、`web/src/components/PostFields.tsx`。

**修正:** 文字表示とAPI制限の検査を整理し、日本語の投稿体験を阻害する暫定制限を解消する。APIの境界は日本語・絵文字・結合文字で確認した上で確定する。今回、実Threads側の境界までは検証していない。

**受け入れ条件:** 167文字を501「文字」と案内しない。日本語・英数字・絵文字混在の境界テストを持ち、フロントとバックエンドの扱いが一致する。

### 4. [P1・画面で再現] AI接続テストが入力中の設定を試していない

**再現:** Gemini保存済みの設定画面でOpenRouterを選択 → モデルが `anthropic/claude-sonnet-4.6` に変わる → 保存せず「つながるか試す」。結果は **「つながりました（gemini-2.5-flash / 2ms）」**。

**原因:** `runTest()` はprovider/modelを送らず、サーバー保存モードでは入力中のキーも送らない。サーバーの `/ai/test` は保存済み設定で実行する。

参照: `web/src/screens/Settings.tsx:328`、`web/src/api/ai.ts`、`worker/src/routes/ai.ts:299`。

**修正:** 入力中の構成でテストし、成功した構成を保存できる流れにする。簡易修正なら未保存変更中のテストを止め、「保存済み設定をテスト」と対象を明示する。

**受け入れ条件:** プロバイダー・モデル・キーのいずれを変えても、別の保存済み設定の成功を新設定の成功として表示しない。

### 5. [P1・コードで確認] 端末保存からサーバー保存へ戻すとキーを失う経路がある

**条件:** 端末にだけキーがある状態でスイッチをオフにし、キーを再入力せず「保存する」。

**原因:** `commit(true)` は入力欄が空ならキーを送らない。サーバーは直前が端末保存なので保持できる暗号化キーを持たない。保存成功後、フロントは `writeClientKey(null)` を実行して端末のキーを消す。

参照: `web/src/screens/Settings.tsx:290`、同`:307`、`worker/src/routes/ai.ts:264`。

**修正:** サーバー保存へ移す対象キーを明示し、既存端末キーを使用するか再入力を要求する。保存先に有効なキーが確保できるまで移行元を消さない。

**受け入れ条件:** 保存場所の往復でキーが失われない。キー未確保の状態を成功表示しない。認証キーを扱うため、本レビューでは実キー変更による再現はしていない。

### 6. [P2・画面で再現] タブ移動で未保存原稿を失う

**再現:** 「作る」で本文を入力 → 下部「キュー」 → 下部「作る」。本文は `0 / 500` へ戻る。離脱確認も復元もない。

参照: `web/src/screens/Create.tsx:60`、`web/src/components/Shell.tsx`。

**修正:** アカウント単位の下書き自動保存と復元。保存中・保存済み状態を表示し、復元できない場合のみ離脱確認を出す。

**受け入れ条件:** タブ移動・再読込後に本文、コメント、素材、指示が復元される。

### 7. [P2・画面で再現] ダイアログのフォーカスが背後へ抜ける

**再現:** 設定の「診断」を開く → Tab。`document.activeElement` の表示文字は背後の「トークン延長」で、dialog配下ではなかった。

**原因:** Sheetは `aria-modal=true` を付けているが、初期フォーカス・フォーカストラップ・背景のinert化を実装していない。

参照: `web/src/components/Sheet.tsx:38`、同`:72`。

**修正:** 開いたらダイアログ内へフォーカスを移し、Tab/Shift+Tabを内部に閉じ込める。閉じたら起点へ戻す。Drawerも同じ観点で点検する。

**受け入れ条件:** キーボードだけで開閉でき、背景の操作を実行しない。

### 8. [P2・画面とコードで確認] 予約一覧が遠い予定から並ぶ

**確認:** 予約が9/11→9/10→9/9→9/8→9/7の順。次に出る9/7が一番下。

**原因:** 状態に関係なく `ORDER BY COALESCE(scheduled_at, created_at) DESC LIMIT 200`。

参照: `worker/src/routes/queue.ts:123`。

**修正:** 予約は近い日時順、履歴は新しい順。200件を超える場合も直近の予約が落ちない取得方式にする。承認待ちは期限順で独立表示する。

**受け入れ条件:** 直近の投稿と期限が迫った承認が先頭で分かる。

## 商品体験として改善すること

### A. ホームの先頭を「今日やること」にする

現状は数字と過去投稿が中心。最上部に次の投稿カード、承認待ち件数、失敗・接続切れ、参考情報の残量をまとめる。「確認して承認」「原因を直す」「ネタを足す」へ直接進める構成にする。数字と分析はその下に置く。

### B. 自動運用の状態を一目で判断できるようにする

確認時は「動いています」「続けて2回失敗」「1日2本」「1日の上限1本」が同時に表示されていた。ログには参考情報の再利用制限で生成できなかった記録もある。

優先順位を「要対応 → 次の実行 → 運用ルール → 実績」の順にする。矛盾する本数設定は保存時に調整または説明する。利用可能な参考情報と再利用可能日を見せ、材料不足をシステム障害と区別する。

現行実装は参考情報1件を生成に使うと7日以内は使い回せない。週14本の運用に参考情報2〜3件だけでは継続できないので、オンにする前に見通しを説明する必要がある。素材から複数の切り口を抽出して蓄積する案も検討できる。

参照: `worker/src/jobs/plan.ts:59`、`web/src/screens/Autopilot.tsx`、READMEのセットアップ手順。

### C. 設定を目的ごとに分け、保存方式を統一する

現在は7セクションが一列で、AIは保存ボタン、通知は即保存。AI欄にもサーバー状態と未保存の入力が混在する。

「接続」「AI」「通知」「データ・契約」に分け、最初の一覧には接続正常／未設定／期限間近を表示する。未保存変更は明示し、プロバイダー変更時に旧キーを登録済みと見せない。「買い手のキー」は「あなたのAPIキー」にする。高度なモデル名入力は詳細設定へ寄せる。

### D. 初回接続を案内し、未接続でも設定を開けるようにする

接続画面はMeta開発者設定の文字説明が中心で、READMEの別マニュアルURLは未記入。購入直後のユーザーが最も詰まりやすい工程なので、実画面に沿った手順、所要時間、進捗、エラー別復帰を用意する。

`RequireAuth` はアカウント0件だと設定を含む全 `/app/*` を `/connect` へ送る。未接続の利用者もライセンス、AI設定、退会、ログアウトに到達できる導線が必要。

参照: `web/src/screens/Connect.tsx`、`web/src/App.tsx`。

### E. PCは幅を使い、スマホは操作を短くする

現行の430px中央固定はスマホに一貫性がある一方、PCでも原稿比較と分析が細長い。PCはナビゲーション＋作業領域＋プレビュー／候補比較へ広げる。スマホは主操作を下に固定し、3つのコメント欄は必要に応じて追加する。

設定の「診断」「トークン延長」「外す」は `btn-quiet` 単独使用によりブラウザー既定の角張った枠が出ている。ボタンの基本スタイルを共通化する。補足文字も薄く小さいため、読みやすさを上げる。

### F. 自動化の品質を測れる検証を追加する

既存465テストは有用だが、フロントの状態遷移を保証していない。今回の再現操作をブラウザーテストとして追加する。APIの成功だけでなく、初回接続→初回下書き完成時間、下書きの採用率、手直し量、承認漏れ、連続運用日数を測る。
