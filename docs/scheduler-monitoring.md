# 定期実行の到達確認

`GET /api/admin/scheduler-status` を既存の `X-Admin-Secret` ヘッダで呼ぶ。一般ユーザーのログインCookieだけでは参照できない。公開 `/api/health` には内部状況を追加しない。

レスポンスは環境名・モード・確認日時と、Cronごとの以下の情報だけを含む。

|項目|意味|
|---|---|
|lastScheduledAt|Cloudflareが通知した予定時刻|
|lastStartedAt|Workerが実際に開始を記録した時刻|
|lastFinishedAt|最新の呼び出しが終了を記録した時刻|
|lastSucceededAt|最後に正常終了を記録した時刻|
|lastFailedAt|最後に失敗を記録した時刻|
|status|not_observed / started / success / error / paused|
|stale|開始の記録が未到達、または目安時間を超過|

全時刻はUTC。未到達は成功として扱わず `not_observed` とする。staleの目安は毎分Cronが5分、毎時Cronが90分、日次Cronが26時間。これは障害を検知する手掛かりであり、実行時刻の保証や自動通知サービスではない。

本番のモード `job_dispatch` は、Cronからジョブ投入・Queueへの引き渡しまで完了した証拠。非同期ジョブそれぞれの完了、API同期成功、投稿成功は別途 `jobs` / `queue` の結果で確認する。失敗した呼び出しのPromiseを再びrejectするため、D1の監視書き込みに失敗した場合もCloudflareには実行失敗として伝わる。監視テーブルに例外の本文、投稿、アカウント情報、Secretは保存しない。

ステージングは毎分1件のCronだけを登録し、モード `trigger_monitor_only` として到達記録だけを行う。アカウントが接続されていても、ジョブ投入・Queue配送・AI生成・Threads取得/投稿・トークン更新・メール送信は開始しない。`npm run check:staging` は他のCronや複数Cronの追加を拒否する。ステージングでの成功を本番Cronの動作確認に代用しない。

メンテナンス中も開始は記録し、状態を `paused` にする。ジョブ処理を実行しないため、新しい成功日時は付けない。

## リリースと予算

`0008_scheduler_health.sql` を適用してからWorkerをデプロイする。固定のCronごとに最新情報を1行で保持するため、通常は本番3行、ステージング1行。履歴が無制限に増える構成ではない。

監視書き込みは通常2クエリ（開始・終了）、終了記録の失敗を再記録するときも最大3クエリの専用予算に制限。無料Cronは作業8 + 台帳37 + 監視3 = 最大48 D1操作とし、Queue用に2枠残す。通常のQueueジョブ用予算は変更しない。

デプロイ後に各環境の管理APIを読み、実際の予定時刻以降の開始/終了記録が増えることを確認する。`stale` や未到達が続く場合はCloudflare側の登録・デプロイ・イベント/ログを確認する。ローカルテストで `scheduled()` を呼び出せたことだけでは、Cloudflareが定期的に呼び出す保証にならない。

## テスト

監視専用Cronの副作用なし、管理者限定、失敗時のPromise rejection、監視書き込み失敗、メンテナンス、重複呼び出し時の古い状態による上書き防止、監視予算3件上限を検証。関連5ファイル32ケースと型チェック・ステージング設定チェックを通過。
