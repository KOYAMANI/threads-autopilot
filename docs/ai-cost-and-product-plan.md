# AI原価・無料提供・将来の課金設計メモ

更新日: 2026-09-10

## この文書の位置づけ

この文書は、投稿生成のAI費用を誰が負担するか、講座生へどこまで無料提供するか、一般公開後にどの段階で課金を導入するかを判断するための設計メモ。

- 現時点では**提案**であり、課金開始・プラン変更・App Store公開を決定するものではない。
- 現在の買い切りライセンス、BYOK、3アカウント上限は変更しない。
- 先に実利用のトークン量と完了1回あたりの原価を記録し、その実測から料金を決める。
- 金額は2026-09-10時点の公開料金を使う。モデル料金は変わり得るため、実装へ単価を直書きしない。

## 結論

当面は、現在の**利用者自身のAPIキー（BYOK）を維持**して試験運用するのが最も安全。現在のアプリではAI費用は基本的に利用者のGoogle/OpenRouter側へ発生し、運営が全利用者分を負担する構造ではない。

講座生に「アプリ利用だけでなくAI生成費用も含めて無料」で提供したい場合は、いきなり月額課金を作るのではなく、次の順序がよい。

1. AIの各上流リクエストについて入出力トークンと推定原価を記録する。
2. 講座生だけに運営負担の月間生成枠を設定する。
3. 利用者単位と運営全体の上限、停止スイッチを入れる。
4. 1〜2か月の実測後、一般利用者向けの月額または追加クレジットを判断する。

App Storeは集客やネイティブ体験が必要になった時の選択肢であり、決済を楽にすることだけを目的に今移行する優先度は低い。現在のCloudflare Workers + React PWAに、ネイティブ配布、審査、StoreKit、購入状態同期という別の運用が追加されるため。

## 現在の実装から分かったこと

### 商品とAI費用の前提

- Web/PWA、Cloudflare Workers + D1 + Queuesで稼働する。
- 商品設計は買い切りライセンス。月額課金は未実装。
- Threadsアカウントは1利用者につき最大3件。`worker/src/lib/accounts.ts` の `ACCOUNT_LIMIT = 3` に固定されている。
- AI設定はThreadsアカウント単位ではなく利用者単位。`ai_settings.user_id` が主キー。
- AIキーは利用者が登録し、D1へ暗号化保存するBYOK方式。
- 現在の通常UIはGemini `gemini-3.5-flash-lite` に固定されている。過去仕様にはOpenRouterも残るため、料金設計では「現在実際に使う経路」と「旧互換経路」を区別する。
- AIを使うのは投稿の生成・修正・Autopilotの下書き生成。分析、採点、集計、型や投稿枠の選択、重複判定にはAIを使わない。

このため、「無料プランは分析のみ」という分け方は現在の実装と相性がよい。AIを止めても分析機能の主要部分は残る。

### 画面上の生成1回と、実際のAIリクエスト数は違う

現在の生成処理は複数工程である。

| 操作 | 通常の上流AI呼び出し | 追加が起きる条件 |
|---|---:|---|
| 型を参考に3案生成 | 3回 | 構成抽象化1回 + 本文生成1回 + 添削1回 |
| 資料・テーマから生成 | 2回 | 本文生成1回 + 添削1回 |
| 指示で修正 | 2回 | 本文生成1回 + 添削1回 |
| 接続確認 | 1回 | 短い生成 |
| Autopilotの1案 | 通常2回 | 本文生成1回 + 添削1回 |

本文検証に通らない場合、構成処理はもう1周するため通常より最大2回増える。さらに通信障害などで各呼び出しが再試行される場合がある。したがって、現在の `audit_log` にある `ai_request` の件数は「利用者が生成APIを操作した回数」であり、Googleへ送った実リクエスト数、トークン数、請求額ではない。

現在の1分10回制限も画面側のAPI操作を制限するだけで、月間原価の上限にはならない。

## 2026-09-10時点の参考単価

現在固定しているGemini 3.5 Flash-Liteの標準有料枠は、Google公式料金ページ上で次の単価。

- 入力: 100万トークンあたり $0.30
- 出力: 100万トークンあたり $2.50
- 出力料金にはthinking tokensを含む。
- Free Tierは入出力無料だが、上限はプロジェクト・モデル・利用Tier等で異なり、保証された商品枠として扱わない。

## 原価の試算

式は次の通り。

```text
推定原価USD
= 入力トークン / 1,000,000 × 入力単価
+ 出力トークン / 1,000,000 × 出力単価
```

以下は実測ではなく、料金判断のための仮置き。為替は比較用に1ドル150円として併記するが、商品価格の固定換算には使わない。

| ケース | 1回の上流呼び出し | 上流呼び出し数 | 生成操作1回の概算 |
|---|---:|---:|---:|
| 軽い | 入力1万 / 出力2千token | 3回 | $0.024、約3.6円 |
| 標準 | 入力2万 / 出力4千token | 3回 | $0.048、約7.2円 |
| 重い・修復あり | 入力5万 / 出力8千token | 5回 | $0.175、約26.3円 |

標準ケースなら月1,000回の生成完了で約$48、比較用換算で約7,200円。重い入力、thinking tokens、再試行、失敗して結果を返せなかった呼び出しも請求対象になり得るため、完成した回数だけを数えると原価を過小評価する。

現在は資料を合計60,000文字まで受け付け、同じ参考情報を生成と添削で繰り返し送る。少数の長い資料や修復ループが平均原価を押し上げる可能性がある。一方、BYOKを維持する限り、このAI原価は原則として運営負担ではない。

## 提供プランの段階案

### Phase 0: 現在〜小規模試験

対象はオーナーと初期講座生。課金連携は作らない。

- アプリ利用料: 講座生は無料。
- AI: 原則BYOK。
- アカウント数: 現状の最大3件を維持。
- 目的: 投稿生成の利用回数、トークン量、失敗率、1完了あたり原価を測る。
- 案内では「アプリ無料」と「Google等のAI利用料」を分けて明記する。Free Tierの利用可否や上限を保証しない。

この方式は運営原価が読みやすい反面、APIキー発行と課金設定が利用開始のハードルになる。

### Phase 1: 講座生向けの運営負担枠

APIキー設定が離脱要因だと確認できた場合だけ導入する。

- 講座生はAPIキーなしでも生成できる。
- 月30〜100回など、利用者に分かる「生成完了回数」で上限を表示する。
- 内部では上流リクエスト、トークン、推定原価をすべて計測する。
- 生成に失敗した場合の枠返却ルールを決める。利用者起因の入力エラーは消費しない。上流AIへ送信後の失敗は、UX上は枠を戻しても原価台帳には残す。
- 運営全体の月間予算上限を設け、80%で警告、100%で新規生成を停止する。
- BYOKへの切り替えを残し、上限到達後も自分のキーなら使えるようにする。

講座生無料が期間限定の場合は、ライセンスの有効期限または特典期限を明示する。「永続無料・無制限」は継続的なAPI費用と相性が悪い。

### Phase 2: 一般公開

最初から月額だけにせず、次の構成を候補にする。

| 区分 | 分析 | アカウント | AI生成 | 費用負担 |
|---|---|---:|---:|---|
| Free | 可 | 1件 | お試し0〜数回、または不可 | 運営の小さな獲得費 |
| Academy | 可 | 3件 | 月間枠あり | 講座料金・販促費に内包 |
| BYOK | 可 | 1〜3件 | 利用者の残高内 | 利用者 |
| Pro候補 | 可 | 3件以上を検討 | 月間枠 + 追加クレジット | 月額または年額 |

決済実装を急がない場合は、まず買い切りライセンス + BYOKを一般販売し、運営負担AIが必要な人だけ後から月額または追加クレジットへ移す。単発クレジットにも決済・返金対応は必要だが、解約、更新失敗、日割り、休止、プラン変更といったサブスクリプション固有の状態は減る。

## 実装するなら必要な設計

### 1. 権限をライセンス状態から分離する

現在は買い切りライセンスの `unused|active|revoked` と、コードに固定された3アカウント上限が中心。将来のプラン差は、ライセンスの有効性とは別のentitlementとして表す。

例:

```text
plan_code                 free | academy | byok | pro
account_limit             1 | 3 | ...
ai_funding_mode           none | byok | platform | hybrid
monthly_generation_limit  0 | 30 | 100 | ...
benefit_expires_at        nullable
```

初期段階では決済サービスを正本にしない。アプリのentitlementを正本にし、管理者が講座生へ付与できるようにする。将来決済を追加したらWebhookから同じentitlementを更新する。

### 2. AI利用台帳を追加する

`audit_log` は監査用のまま残し、原価計算には専用テーブルを使う。最低限、上流AIへの1リクエストごとに次を保存する。

```text
ai_usage_events
- id
- user_id
- account_id
- generation_task_id
- operation        abstract | compose | edit | retry | test | autopilot
- provider
- model
- billing_source   byok | platform
- input_tokens
- cached_input_tokens
- output_tokens
- thinking_tokens  取得できる場合
- upstream_requests
- estimated_cost_microusd
- pricing_version
- status
- created_at
```

- Gemini応答の `usageMetadata` を読み、現在捨てているトークン情報を記録する。
- 推定単価は日付つきの料金表で管理し、イベント作成時の `pricing_version` と推定額を残す。
- 本文、参考資料、AIキー、生の上流応答は原価台帳へ保存しない。
- 推定額は運用判断用。最終的な請求照合はプロバイダーの請求画面・請求データを正とする。

### 3. 「枠」と「実原価」を別に扱う

利用者には分かりやすい生成回数を見せ、内部ではトークン原価を守る。

- 生成開始時に1枠を予約する。
- 同じ `generation_task_id` の再送で二重消費しない。
- 完了時に確定する。
- 上流へ一度も送らず入力エラーになった場合は予約を戻す。
- キャンセル、タイムアウト、部分成功時の利用者枠ルールを決める。
- 内部原価台帳は、利用者枠を戻した場合でも実際に送った上流リクエストを残す。

生成回数だけでなく、利用者ごとの月間推定原価にもハード上限を持たせる。極端に長い資料を繰り返す1人が全体予算を使い切るのを防ぐ。

### 4. 運営キーの安全装置

- 運営用AIキーはD1の利用者設定へ複製せず、Cloudflare Secretとして管理する。
- BYOKと運営キーのどちらを使ったかをサーバー側のentitlementから決める。クライアント指定を信用しない。
- 利用者単位、全体単位、1分単位、1日単位、月単位の上限を持つ。
- `PLATFORM_AI_ENABLED` のような全体停止スイッチを用意する。
- 予算80%到達、急増、同一利用者の異常な失敗率を管理者へ通知する。
- 接続確認ボタンで運営枠を消費させない。運営キー利用時は設定画面の接続確認を不要にする。
- 429の日次上限、認証失敗、入力不正は自動再試行しない。503等の一時障害だけ限定的に再試行する現方針を維持する。

### 5. 原価を下げる順序

品質を落とすモデル変更より先に、重複送信を減らす。

1. 生成・添削ごとのトークン実測。
2. 長い固定プロンプトや同じ参考のキャッシュ適用可否を確認。
3. 添削工程が品質・成功率をどれだけ改善したかを計測し、不要なケースだけ省略。
4. 3案が常に必要かを確認。無料枠は1案、有料枠は3案という分離も候補。
5. 資料上限を「文字数」だけでなく推定トークンと利用枠に応じて制御。
6. Batchは即時生成のUXと合わないため、Autopilotなど非同期処理でのみ検討。

## App Storeについて

現在の判断は**保留**。

- Apple Developer Programは年99米ドル。
- デジタル機能の解放は原則In-App Purchaseが必要。
- Small Business Program対象者は有料アプリとアプリ内課金の手数料が15%。
- Appleが購入・請求導線を提供しても、アプリ側には購入状態の確認、失効、返金通知、権限の取り消し、復元処理が必要。
- 現在のPWAをApp Storeへ出すには、配布方式、審査、プライバシー申告、StoreKit連携、更新運用が増える。

一次資料:

- [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- [Apple Developer Program membership](https://developer.apple.com/programs/whats-included/)
- [App Store Small Business Program](https://developer.apple.com/app-store/small-business-program/)
- [In-App Purchase](https://developer.apple.com/in-app-purchase/)

次の条件が揃った時に再検討する。

- iPhoneのホーム画面追加では獲得・継続利用に明確な問題がある。
- App Store検索からの集客仮説がある。
- Push、バックグラウンド処理、共有メニュー等のネイティブ機能が売上に効く。
- Web課金よりApp Store手数料を払う方が、決済・税・獲得を含めて有利だと数字で説明できる。

## 計測する指標

料金を決める前に最低1〜2か月、次を集計する。

- 月間AI利用者数、生成開始数、生成完了数。
- 1完了あたりの上流リクエスト数、入力・出力・thinking tokens。
- 1完了あたり推定原価の中央値、p90、最大値。
- 失敗したAI呼び出しにかかった原価。
- 修復ループ率、通信再試行率、部分成功率。
- 1人あたり月間生成回数と推定原価の分布。
- 1案と3案での保存率、予約率、公開率。
- APIキー設定画面から生成完了までの離脱率。
- 分析のみの利用者がAI生成を必要とする割合。

月額料金を決める場合は平均ではなくp90原価を基準にし、決済手数料、返金、サポート、Cloudflare、メール、障害時の余白を加える。

## 先に決める必要があること

- 「講座生は無料」に、AIプロバイダーの利用料まで含むか。
- 含む場合、月間何回、いつまで、超過後は停止かBYOK切り替えか。
- 運営が許容するAI予算の月額上限。
- 一般無料ユーザーへAIのお試しを付けるか。付けるなら本人確認前の濫用対策。
- 無料1アカウント・有料複数アカウントを採用するか。現在は全利用者3件固定なので実装変更が必要。
- 将来の決済が月額、年額、追加クレジット、買い切り+BYOKのどれか。
- 買い切りに含むホスティング期間。現SPECでも年数は未確定。

## 推奨する次の実装順

課金機能より先に次を行う。

1. `usageMetadata`を取得し、AI利用台帳へ記録する。
2. 管理者向けに日別・利用者別の生成完了数、トークン、推定原価を表示またはCSV出力する。
3. entitlementを導入し、アカウント上限とAI利用可否をコードの固定値から分離する。
4. 講座生数名だけで運営負担枠を試し、上限と停止スイッチを検証する。
5. 実測後に初めて一般向け価格と決済手段を決める。

この順序なら、決済連携、月額更新、返金対応を先に抱えずに、課金が本当に必要か、必要ならいくらかを判断できる。
